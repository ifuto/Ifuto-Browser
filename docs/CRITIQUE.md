# CRITIQUE.md — シニアグラフィックスアーキテクトによる贅沢な無駄の監査

> 筆者: 不要な複雑さを心から憎む偏屈なシニアグラフィックスアーキテクト。
> 対象: Ifuto Browser（HEAD 2ba2435）全ソース精読 + 実測に基づく。
> 態度: 「全部自作」はユーザ決定であり製品のアイデンティティだから尊重する。だが
> **その枠の中で犯している無駄・車輪の再発明・性能のドブ捨て**は遠慮なく指摘する。

---

## 1. 総評

このコードベースは「天才のためのコード」だ。密度が高く、計測で裏取りされた
設計判断が各所に埋まっていて、学ぶ価値は高い。だが、**天才は道具であって目的ではない**。
以下の指摘は「直せ」ではなく「俺はこう考える、お前はどうする」の形で書く。

## 2. 車輪の再発明（意図的か、惰性か）

### 2.1 生 X11 プロトコル直書き（src/gui/x11t.c, 550 行）
Xlib はこの世に存在する。XCB も存在する。それを捨てて、**ワイヤプロトコルを手で
組み立てる**のは、文字通り車輪の再発明だ。XAuth cookie 解析、リクエスト長分割、
リプライ同期——全部、過去 30 年の X 開発者が踏んだ地雷を自分で踏み直している。
しかも実装範囲は「動く最小スライス」で、将来 X の機能（XRender、XInput2、
マルチモニタ DPI など）が必要になった瞬間にここが首を絞める。
**しかし**: 「ldd = vdso/libm/libc/ld」はこの製品の看板であり、ユーザ決定の
「依存ゼロ」は譲れない。つまりこれは**契約上の正しい選択**だ。ただし、
「自分で書いたから Xlib より安全」と考えるのは危険——プロトコル実装のバグは
Xlib のバグより新しい分だけ確実に多い。台帳に「X11 直書きはメンテ負債」と記せ。

### 2.2 自作 seccomp-BPF（src/sandbox.c）
libseccomp は存在する。BPF を手書きしているのは「依存ゼロ」のためだが、
**seccomp-BPF の記述ミスはセキュリティ境界の穴そのもの**だ。ここは車輪の
再発明で得をする場所ではない。少なくとも「allowlist 非一致 = KILL」という
fail-closed 設計は正しい（称賛する）。改善: フィルタを機械生成（テストで
syscall 表と突合）する仕組みを入れるべき。

### 2.3 自作 JS エンジン（akl, 5,053 行）
QuickJS は 2020 年に Fabrice Bellard が 2 万行で書いた。それを「1 万行で書ける」
と挑むのは傲慢だが、**これはユーザ決定**であり、しかも「JIT なし = W^X 構造保証」と
いう QuickJS にはない一線がある。正当。ただし下記 §4 の複雑さの指摘は別問題。

### 2.4 自作フォント（tools/gen_font16.py, 2,228 行）
漢字 103 字をストローク DSL で手書き。残りは豆腐。**2026 年に、GPU を積んだ
マシンで、5x7 ピクセルのビットマップフォントを XPutImage する**。これは
「ハードウェア性能をドブに捨てる」の見本である。フリーフォント（Noto CJK は
OFL ライセンス）を埋め込むのは「外部フォント持ち込みゼロ」という自己制約への
違反だが、その制約自体が**効用関数の誤り**だ。文字を表示するのがブラウザの
仕事であって、文字を彫るのは仕事ではない。
**ただし**: これはユーザの趣味・製品の個性であり、攻撃する価値は低い。
代替案: フォントスロットをプラグイン化し、システムフォントがあればそれを使い、
無ければ自前フォント——の順で解決する層を作ること（GUI の最終形のためには必須）。

## 3. ハードウェア性能をドブに捨てている箇所

### 3.1 セル座標系（8px×16px）
レイアウトは整数セル、行高 16px に 5x7 フォント = **1 行の 56% が空白**。
サブピクセルもアンチエイリアスも字間調整も存在しない。モダンな GPU は
三角形を 1 秒に数十億個流せるのに、このブラウザは 5x7 の点を並べている。
ロードマップの v0.3「ソフトピクセルラスタ + backend 境界凍結」は正しい方向だが、
完了基準「同一文書のセル版・ピクセル版で視覚一貫」は**発想が逆**だ。
ピクセル版が製品で、セル版はデバッグ用の検証 backend に過ぎない。基準を
「ピクセル版の画質（AA・行間・字間）」に置け。

### 3.2 毎フレームの XPutImage
GUI は行ハッシュで差分を検出して dirty 行だけ XPutImage している——これは
賢い（褒める）。しかし**根本は「フレームバッファ全体を毎回サーバに送る」**
アーキテクチャだ。MIT-SHM は sandbox.c の台帳に「実装済み」と書いてあるのに
GUI は使っていない。`shmget` で共有メモリを張れば XPutImage のコピーが
ゼロになる。**やれ**。

### 3.3 16MB マークダウンへの過剰適応
parse 7.2ms / layout 7.9ms / render 2.4ms（2MB）を 123ms（16MB）まで
絞るために、slim-DOM・窓グリッド・行スイープ・入力 compaction・2-slice 並列
という**5 層の機構**を積んだ。これは「1 物理コアの箱」で「1 枚のテキスト文書」を
速くするためだ。実ブラウズの主戦場は「タブ 50 枚 × 画像 × JS × ネットワーク待ち」で、
そこではこの 5 層のうち効くのは compaction くらいだ。**計測文化は正しいが、
計測対象の選択が自己愛的**。BENCH.md に「タブ 50 枚の実ブラウズ模擬」を追加せよ。

### 3.4 md.c の SIMD と 2-slice 並列
AVX2 可視ラン走査（fitdom CJK SIMD）と 2 スレッド並列 parse。この箱は
1 物理コア + 2HT。**HT で並列化して得られるのは騒音との戦いだけ**だ。
serial≡sliced オラクルという検証コストまで払っている。機構としての正しさは
認めるが、これは「性能をドブに捨てている」の逆ではなく「検証予算をドブに
捨てている」に近い。優先度を下げよ。

## 4. 無駄に複雑な箇所（akl エンジン）

### 4.1 融合オペコードの雪だるま
OP_CJMPF_MODG / OP_CJMPF_MULGG / OP_LOOPINC_GV / OP_ADD_GX / OP_GADD_G / OP_LADD_LL
……**80 超のオペコードのうち 3 分の 1 は「特定のソース形の 2〜3 命令を 1 命令に
畳んだ」融合命令**だ。fib(22) が 1.474ms → 1.502ms になるのを恐れて、だ。
計測は正しく、採用判断も正しい（BENCH.md の台帳は模範的）。だが、この層は
**新機能を追加するたびに「dispatch 表・verifier・CoJIT・双子バイナリ」の
4 箇所を同期させる税金**を課す。今回の私の作業（配列・クロージャ・this）も
この税金を払っている。結論: 融合は止めないが、**新規融合の追加は「実測 3% 以上 +
バイト列差分ゼロ」の証明がない限り禁止**と明文化せよ。

### 4.2 例外の cold 分離
try/catch の機械語を cold 関数に隔離してホットループの I$ を守る——これは
GCC の `__attribute__((cold))` で実現できることを手でやっている。正しい方向だが、
「なぜ」をコメントに書かないと未来の自分が「最適化だ」と消してしまう。
コメントは十分に書いてある（褒める）。継続せよ。

### 4.3 バイト列オラクル 21 件の重石
`oracle/forged.*` の byte-exact 比較は「出力の全バイト」を凍結する。これは
検証としては最強だが、**レンダラを 1 ピクセルも動かせなくする**。セル描画の
バグ修正ひとつで 21 件全部の sha256 が変わる。オラクルの粒度を「バイト列」から
「意味的等価（DOM 構造・レイアウト座標・色）」に上げる時期が来ている。
とはいえ現状の「1 bit も変えない」はプロジェクトの美徳なので、私も
**今回の作業では 21/21 を守る**（文字コード・script 実行のオラクルは維持する）。

## 5. 褒めるべき（贅沢だが正しい）

- **arena 一括所有**: dangling を構造排除する設計は、C で書くならこれしかない。
- **計測規約**: paired interleaved + 符号検定 + byte-exact。この規律は業界上位 1%。
- **kill switch 文化**: IF_SCRIPT=0 / IF_MD_PAR=0 / IFUTO_NO_STORE 等。観測点と
  安全弁が一元管理されている。
- **「未対応は明白に落とす」**: `++` を lex で拒否して二重 unary の黙認を防いだ
  判断（akl.c のコメント）は、このプロジェクトの良心そのもの。
- **ツリービルダの WPT 100.0%**: 1922/1922。これは狂気の沙汰。敬意を払う。

## 6. 私が今回やること・やらないこと

### やる（v0.3 目標 = Akl 完全実装 + HTTPS 完全実装）
1. **Akl 言語の完成**: 配列・ブラケットアクセス・関数式/クロージャ・`this`・
   三項演算子・do-while・switch・`++`/`--`・複合代入・ビット演算・
   Math/String/Array 組込。仕様は「動く JS の常識範囲」で、対応しないものは
   AKL_COMPAT.md に実測で明記（このプロジェクトの掟）。
2. **DOM バインディング拡張**: querySelector・getElementsByTagName・
   getAttribute/setAttribute・style 書換（ロードマップ v0.3 の定義どおり）。
3. **HTTPS**: TLS は**自作しない**。BearSSL（MIT、battle-tested、ロードマップが
   既定の「BearSSL 等」）を vendored 静的リンクする。CA はシステムストアを読む。
   **TLS を自作するのは、私でも正気を疑う。** 車輪の再発明にも限度がある。
4. 上記に付随する docs 更新（AKL_COMPAT / SCRIPTING / ARCHITECTURE / README / BENCH）。
5. 検証: `make test`（623,986 checks × 2）・oracle 21/21・WPT・guismoke・golden・
   fuzz を全て緑に保ったまま。

### やらない（理由つきで）
- セル→ピクセルラスタの全面置換（ロードマップ v0.3 の残り部分。今回の指示は
  Akl と HTTPS。次ターンでやるなら backend 境界の凍結から）。
- X11 直書きの撤去（ユーザ決定の依存ゼロに抵触。台帳に残す）。
- フォントの外部化（ユーザの趣味。プラグイン化の提案だけする）。
- 自作 TLS（禁止。BearSSL を採用）。
